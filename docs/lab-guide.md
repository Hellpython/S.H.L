# 연구실 시험 안내 (ESP32 처음 쓰는 사람용)

이 문서는 "어떻게 연결하고, 어떤 명령을 치고, 무엇을 보면 되는지"를 설명한다.
실제 기록은 [lab-test-checklist.md](lab-test-checklist.md)에 한다.

모든 명령은 맥북 터미널에서 프로젝트 폴더로 이동한 뒤 실행한다.

```sh
cd ~/developments/child-safety-iot
./scripts/lab.sh help
```

## 1. 이번 시험에 필요한 것 / 필요 없는 것

| 구분 | 부품 | 비고 |
|---|---|---|
| **필수** | ESP32 보드 2대 | 1대 = 키링(송신), 1대 = 도로변(수신). 발표 자료상 "ESP32 DevKitC" — 실물 모델 확인 필요 |
| **필수** | 데이터 전송 가능한 USB 케이블 2개 | 보드 포트 모양(Micro-USB / USB-C)에 맞게. 충전 전용 케이블은 포트가 안 생김 |
| **필수** | 맥북 USB 포트 2개 또는 어댑터 | 맥북이 USB-C만 있으면 USB-C ↔ 보드 케이블 또는 어댑터 필요 |
| LED 시험 시 | LED 1개 + 저항 + 브레드보드 + 점퍼선(수-수) | **LED 종류를 확인한 뒤에만** 연결 (4절) |
| 있으면 좋음 | 휴대용 보조배터리 + USB 케이블 | 키링 보드를 맥북과 떨어뜨려 거리 시험할 때 전원용 |
| 있으면 좋음 | 스마트폰 BLE 스캐너 앱(nRF Connect 등) | 키링이 실제로 광고하는지 따로 확인 |
| **이번에 연결 안 함** | HLK-LD2410C(레이더), BH1750(조도), WS2812B LED Bar, HPRO-0063(LED 매트릭스) | 현재 펌웨어가 쓰지 않음. 연결하지 않는다 |

## 2. 보드 확인 (가장 먼저)

1. 보드 금속 덮개(모듈)에 적힌 글자를 사진으로 찍는다. 예: `ESP32-WROOM-32E`, `ESP32-S3-WROOM-1`, `ESP32-C3`.
2. 보드 뒷면·앞면 인쇄(예: `ESP32-DevKitC V4`)와 USB 근처의 작은 칩 이름(예: `CP2102`, `CH340`)도 찍는다.
3. 판단:

| 모듈에 적힌 칩 | 현재 설정(`board = esp32dev`)으로 | 할 일 |
|---|---|---|
| `ESP32-WROOM-32`, `ESP32-WROVER` 계열 (S3·C3 글자 없음) | 그대로 시도 | 없음 |
| `ESP32-S3` / `ESP32-C3` 등 | **그대로 쓰면 안 됨** | 업로드하지 말고 기록. `platformio.ini`의 `board` 변경과 재빌드가 필요(이 칩용 도구는 아직 설치 안 됨 → 인터넷 필요, 미검증) |
| 모르겠음 | 업로드하지 않음 | 사진을 남기고 확인부터 |

공식 문서상 ESP32-DevKitC V4에 사용자 LED는 없고 전원 표시 LED만 있다. 그래서 외부 LED가 필요하다(보드 리비전에 따라 다를 수 있으니 실물 확인).

## 3. 연결 → 포트 확인 → 업로드

### 3-1. 맥북에 연결

1. 한 번에 **한 대만** 연결한다.
2. 보드의 빨간 전원 LED가 켜지는지 본다.
3. `./scripts/lab.sh ports` → 새로 생긴 포트 이름을 적는다. 예: `/dev/cu.usbserial-0001`, `/dev/cu.SLAB_USBtoUART`, `/dev/cu.wchusbserial...`
4. 보드에 마스킹테이프로 **"키링"** / **"도로변"** 라벨을 붙인다.
5. 두 번째 보드를 연결하고 다시 `ports` → 새로 생긴 포트가 두 번째 보드다.

포트 이름은 꽂는 USB 구멍이 바뀌면 달라질 수 있다. 다시 꽂았다면 `ports`로 재확인한다.

포트가 안 보이면 `ports`가 확인 순서를 보여 준다(케이블 교체가 가장 흔한 해결책). 드라이버 설치가 필요해 보이면 **설치 전에 칩 이름을 확인**하고 팀과 상의한다. 공식 문서상 DevKitC의 CP210x 드라이버는 보통 OS에 포함돼 있다. CH340 계열은 확인이 필요하다.

### 3-2. 업로드

```sh
./scripts/lab.sh upload keyring  /dev/cu.<키링 보드 포트>
./scripts/lab.sh upload roadside /dev/cu.<도로변 보드 포트>
```

- 실행하면 역할·보드 설정·포트를 보여 주고 `[y/N]`을 묻는다. **포트가 라벨과 맞는지 보고** `y`를 입력한다.
- 마지막에 `업로드 성공`이 나오면 펌웨어가 보드에 써진 것이다. **BLE 통신이 된다는 뜻은 아니다.**

### 3-3. 업로드가 안 될 때

| 화면 메시지 | 해결 |
|---|---|
| `Failed to connect to ESP32` / `Wrong boot mode` / `Connecting....____` 반복 | **BOOT 버튼**을 누른 채로 업로드 명령을 다시 실행, `Connecting...`이 보이면 버튼을 뗀다 |
| `Resource busy` / `could not open port` | 다른 터미널 창의 시리얼 모니터를 Ctrl+C로 끈다 |
| `No such file or directory` (포트) | 케이블이 빠졌거나 포트 이름이 바뀜 → `ports` |
| 그 밖의 오류 | 오류 메시지 원문을 그대로 사진/복사로 기록 |

버튼 이름: **BOOT**(= GPIO0, 다운로드 모드용), **EN**(= 리셋). 다른 방법으로 다운로드 모드를 넣으려면 BOOT를 누른 채 EN을 눌렀다 뗀다. 업로드가 끝난 뒤 EN을 한 번 누르면 새 펌웨어로 다시 시작한다.

### 3-4. 전원을 껐다 켜도 펌웨어가 다시 도는지

1. USB를 뺐다가 다시 꽂는다(또는 EN 버튼).
2. `./scripts/lab.sh monitor <포트>`를 실행한다.
3. 20초 안에 `[ALIVE] keyring ...` 또는 `[ALIVE] roadside ...`가 나오면 펌웨어가 다시 실행 중이다(약 10초 간격). 이 로그로 어느 보드가 어떤 역할인지도 확인할 수 있다.

## 4. LED 연결 (부품 확인 후에만)

현재 코드는 **도로변 보드의 GPIO23을 HIGH(3.3V)/LOW(0V)로 바꾸기만 한다**(`include/app_config.h`의 `kLedPin`). 어떤 LED를 어떻게 연결할지는 실제 부품 사양을 본 뒤 정한다.

| LED 종류 | 현재 코드로 켜지나 | 비고 |
|---|---|---|
| 일반 LED(다리 2개) | 가능 (저항 필수) | 아래 순서로 |
| WS2812B LED Bar(발표 자료 부품, 선 3개: 5V/GND/DIN) | **안 됨** | 데이터 신호로 제어하는 LED라 라이브러리와 전원 설계가 필요. 이번에는 연결하지 않는다 |
| HPRO-0063 (발표 자료의 LED 매트릭스) | 미확인 | 부품 정체·사양 확인 전 연결하지 않는다 |
| 보드 위 LED | 해당 없음 | DevKitC는 전원 LED뿐(공식 문서) |

일반 LED 연결 전 확인할 것: LED의 순방향 전압(Vf)과 권장 전류(데이터시트·판매 페이지), 긴 다리(+)/짧은 다리(-).

- 저항 계산: `저항(Ω) = (3.3 − Vf) ÷ 전류(A)`.
  계산 예(가정값): Vf 2.0V, 4mA → (3.3−2.0)/0.004 ≈ 325Ω → 330Ω 사용. 실제 값은 부품 사양으로 다시 계산한다.
- 연결 형태(사양 확인 후): `GPIO23 → 저항 → LED(+, 긴 다리) → LED(−, 짧은 다리) → GND`

주의:
- **연결·변경은 USB를 뺀 상태에서** 한다.
- **저항 없이 LED를 GPIO에 직접 연결하지 않는다**(과전류로 GPIO·LED 손상 가능).
- GPIO에 5V를 연결하지 않는다. ESP32 GPIO는 3.3V다.
- GPIO 하나로 LED 여러 개·LED 바·모터를 직접 구동하지 않는다.
- LED가 아예 안 켜지거나, WARNING/WAITING과 반대로 켜지거나, 예상과 다르게 동작하면 **즉시 USB를 뺀다**. 그다음 GPIO23 위치, GND 연결, LED 방향(긴 다리가 저항 쪽)을 다시 확인한다.
  - LED 방향만 뒤집혔다면 보통 **아예 켜지지 않는다**.
  - 상태와 반대로 켜진다면 LED가 3.3V와 GPIO 사이에 연결된 것(active-low)일 수 있다. 현재 코드와 맞지 않는 배선이니 위 연결 형태로 고친다.

## 5. BLE 시험 진행

| 보드 | 펌웨어 | 전원 | 하는 일 |
|---|---|---|---|
| 키링 | `keyring` | 업로드 후에는 보조배터리 또는 맥북 USB | 약 100ms마다 BLE 광고 송출 |
| 도로변 | `roadside` | 맥북 USB(로그를 봐야 하므로) | 1초씩 스캔, 키링을 받으면 WARNING + LED ON |

키링 "OFF" = USB 케이블을 뽑는다(보조배터리 전원이면 배터리 쪽 케이블을 뽑는다).

수신 로그 보기:

```sh
./scripts/lab.sh monitor /dev/cu.<도로변 보드 포트>
```

| 로그 | 뜻 |
|---|---|
| `[ROADSIDE] state=WAITING timeout=3000ms` | 부팅 직후 1번. 모니터를 연 뒤 EN을 누르면 보임 |
| `[ALIVE] roadside ... scans_ok=.. scan_errors=.. state=..` | 약 10초마다(조금 늦을 수 있음). **수신 펌웨어의 반복(loop)이 돌고 있다**는 표시. 스캔·수신이 정상이라는 보증은 아님 |
| `[RX] t=..ms keyring=1 rssi=-55` | 키링 신호 받음 (rssi는 신호 세기, 거리 아님) |
| `[LED] ON` + `[STATE] WAITING -> WARNING t=..ms` | 경고 시작 |
| `[LED] OFF` + `[STATE] WARNING -> WAITING t=..ms` | 신호가 설정 시간 동안 없어서 경고 종료(신호 소실). 마지막 `[RX] t`와의 차이가 종료까지 걸린 시간 |
| `[SCAN ERROR] ...` / `[E] ...` | 스캔 시작 오류 / 라이브러리 오류 — 원문 기록 |

상태 구분:

- **정상 수신 중**: `[RX]`가 계속 나오고, `[ALIVE]`의 `state=WARNING`
- **신호 소실**: `[RX]`가 멈춘 뒤 `[STATE] WARNING -> WAITING`, 이후 `[ALIVE]`만 나옴(`state=WAITING`)
- **수신기 이상 의심**: `[ALIVE]`가 20초 넘게 안 나옴, `scan_errors`가 늘어남, `[SCAN ERROR]` 발생 → 이 동안의 시험은 무효

**로그가 없다고 정상인 것이 아니다.** `[ALIVE]`가 계속 나오는지 확인한다. 단, 스캔 시작 뒤의 일부 실패는 이 펌웨어가 감지하지 못한다([README 알려진 한계](../README.md#알려진-한계)).

모니터 종료는 Ctrl+C. 모니터를 켠 채로는 같은 보드에 업로드할 수 없다.

## 6. 맥북 단위 테스트 (장치 없이)

```sh
./scripts/lab.sh test        # 경고 판단 로직 테스트
./scripts/lab.sh build       # 두 펌웨어 빌드
./scripts/lab.sh doctor      # 도구 점검
./scripts/test_lab.sh        # lab.sh 자체 점검(모의 업로드, 실제 USB 안 씀)
```

연구실에 가기 전과 펌웨어를 고친 뒤에 실행한다.
